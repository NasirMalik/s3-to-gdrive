## Bug found in `s3gdrive`

`ensure_aws_auth()` (line 96) shells out to a command that does not exist:

```python
subprocess.run(["aws", "login"], check=True)   # ← not a valid AWS CLI command
```

The AWS CLI v2 command is `aws sso login`. With `check=True`, the current code raises
`CalledProcessError` the moment a session expires — the exact scenario that just occurred.
Suggested fix:

```python
def ensure_aws_auth():
    result = subprocess.run(["aws", "sts", "get-caller-identity"], capture_output=True)
    if result.returncode != 0:
        print("[aws] Session expired — opening browser to log in ...")
        subprocess.run(["aws", "sso", "login"], check=True)
        print("[aws] Login complete.")
```

A second inconsistency: the README documents OAuth desktop-app credentials at
`~/.s3gdrive_credentials.json`, but the script actually authenticates via
`google.auth.default()` (gcloud application-default credentials). The README setup section
does not match the code.

## Recommended actions

1. **Run the sync manually** from a terminal on your Mac:
   ```bash
   cd ~/Ai-directory/DH-Repos/s3-to-gdrive
   aws sso login
   gcloud auth application-default login \
     --scopes=openid,https://www.googleapis.com/auth/userinfo.email,https://www.googleapis.com/auth/cloud-platform,https://www.googleapis.com/auth/drive
   CONFLUENCE_EMAIL=nasir.mahmood@deliveryhero.com \
   CONFLUENCE_API_TOKEN=<token> \
   ./s3gdrive
   ```
   Do not commit the token — export it from your shell profile or a secret manager.

2. **Apply the `aws sso login` fix** above so expiry produces a clear message instead of a
   stack trace.

3. **Decide how this should be automated.** Browser-based SSO plus browser-based Google
   auth means this workflow cannot run unattended as currently designed. Options:
   - Keep it manual and change the schedule to a weekly *reminder* rather than an execution.
   - Move it to CI (GitHub Actions) with an IAM role via OIDC for S3 and a Google service
     account with domain-wide delegation for Drive — no interactive auth, no local machine
     dependency. This is the durable fix.

4. **Note on the duplicate-upload behaviour:** each run calls `create_drive_folder()`
   unconditionally, so a fresh bucket folder is created every time rather than updating the
   existing one. After several runs the parent folder will accumulate duplicates. Worth
   addressing alongside the CI migration.
